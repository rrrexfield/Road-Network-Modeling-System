# Sprint 2 多模态路网设计（C，本地开发版）

日期：2026-10-30。状态：四模态基础图已实现，尚未集成 API、转换点或跨模态路径。不是 Sprint 2 完整验收报告。

## 入口与数据

从 topology/index.ts 调用 `buildModalTopology(nodes, ways, mode)`，mode 使用 shared 的 car/walk/bike/bus。返回 mode、独立 topology 和准入排除列表 excludedWays。方向与数据质量排除另见 topology.issues，两处诊断均须呈现。

每个模式独立构图和建立禁转索引，禁止跨模式复用 edgeId。原始 highway、tags 不修改；临时有效方向仅用于生成该模式的边，不回写原始 oneway。持久化应使用含模式的数据集标识，例如 wuhan:car；不能直接把另一个模式的规则视为本图规则。

现有 createTopologyReport 标注的是不做模式过滤的输入口径，不能把它的 scope 原样当作多模态报告；A 集成模式报告时应使用这里的 mode 与两类排除列表，尚未改动 API/前端。

## 默认准入矩阵（项目保守策略，非完整地区法规）

普通机动车道路集合：motorway/motorway_link、trunk/trunk_link、primary/primary_link、secondary/secondary_link、tertiary/tertiary_link、unclassified、residential、living_street、service、road。

| 模式 | 无显式权限时默认纳入 |
|---|---|
| car | 普通机动车道路集合 |
| bus | 普通机动车道路集合，加 busway |
| walk | 普通集合去掉 motorway/motorway_link/trunk/trunk_link，加 footway/pedestrian/path/steps/track/corridor |
| bike | 普通集合去掉 motorway/motorway_link/trunk/trunk_link，加 cycleway/path/track |

construction/proposed 始终排除，不因 access=yes 放行。其他不在默认集合中的等级，只有该模式或其车辆父类明确准入才考虑纳入；泛化 access=yes 不把普通步行专用道路变成汽车道路。

car 优先读取 motorcar > motor_vehicle > vehicle > access；bus 为 bus > psv > motor_vehicle > vehicle > access；bike 为 bicycle > vehicle > access；walk 为 foot > access。更具体标签优先。yes/designated/permissive 允许，no/private 排除；destination、customers、permit、dismount 等暂不实现语境推理，排除并记录原值。条件准入或 forward/backward 准入当前保守排除，不按无条件允许处理。

## 各模式方向

- car：oneway:motorcar > oneway:motor_vehicle > oneway:vehicle > oneway。
- bus：oneway:bus > oneway:psv > oneway:motor_vehicle > oneway:vehicle > oneway。
- bike：oneway:bicycle > oneway:vehicle > oneway，因此自行车可显式双向例外。
- walk：普通街道的泛化车辆单行不限制步行；oneway:foot 优先。steps 上的泛化 oneway 作为行人方向；footway/path/corridor 上泛化单行含义可能不清，当前保守标记不支持，不能默认为双向。

模式相关条件方向不计算时段，进入 unsupported-direction 诊断。原 M1 的 motorway/roundabout 默认规则继续用于车辆模式；无明确方向的 motorway_link 不凭经验推断。该方案未处理车道级、转向模式例外、临时封闭、完整地区默认权限等所有 OSM 语义，不能称作生产导航规则。

参考：[OSM access](https://wiki.openstreetmap.org/wiki/Key:access)、[oneway](https://wiki.openstreetmap.org/wiki/Key:oneway)、[自行车单行例外](https://wiki.openstreetmap.org/wiki/Key:oneway:bicycle)。标签层级和模式例外有资料依据，具体默认等级矩阵及保守排除是本项目策略，需 A/B 评审。

## 转换点标记（已实现，尚未验证实际换乘连接）

io/index.ts 提供 extractTransferPoints(raw) 与 getTransferPoints(data,mode?)，输出冻结的 TransferPoint 形状。数据来自原始武汉JSON的节点与way，不来自只保留道路的派生文件；A组装时需明确原始数据加载或转换点缓存方案，当前不修改A的预处理脚本或API。

- 公交类：highway=bus_stop、amenity=bus_station，或 public_transport=platform 且 bus=yes。
- 地铁类：station=subway，或 railway=station 且 subway=yes。
- 停车类：amenity=parking 或 bicycle_parking，保留内部模式区分。
- 节点位置直接使用原始坐标；way采用包围盒中心作展示代表点，内部sources标注bounding-box-center。代表点不保证在多边形内，更不是已核验出入口；当前主要面向武汉，不声称处理跨日期变更线区域。
- 显式access=no/private及条件access排除并报告；这不是完整的站点准入规则解析。
- node和way使用不同数字ID编码（2*nodeId、2*wayId+1），保留源类型与源ID；超安全整数的ID、重复来源、缺失或非法几何明确报告。不按同名合并不同站点，node与way可能描述同一设施，当前不做实体级去重。

模式查询是展示策略：walk显示全部；car显示普通停车；bike显示自行车停车；bus显示公交类。地铁类目前只随walk显示，TravelMode没有rail，不将其当作公交线路。以上只是标记筛选，不能据此断言能换乘。

## 装载策略（A 决策，2026-11-04，issue #33）

### 结论

采用**方案 A：按需懒加载**。某个交通模态的子图、禁转索引与禁转表在**第一次请求该模态时**才构建，之后按 LRU 保留（同一时刻常驻 1 个模态）。四模态的道路 GeoJSON 序列化结果单独缓存（约 26 MB/模态，合计约 104 MB），使地图切换不必重建图。

**否决方案 B（启动时构建全部四份）**：武汉全量实测，四模态全部常驻约需 2.5 GB 堆 / 3.0 GB RSS，与作业四「启动 < 3 s」和 8 GB 笔记本的内存预算冲突；且启动即多花约 16 秒构图。

### 实测数据（武汉全量，Node 22.23.4，6 GB 堆上限）

单模态构图（`buildModalTopology` → `new Graph`）与完整运行时（拓扑 + 禁转索引 + 禁转表 + GeoJSON）的堆占用：

| 阶段 | 增量堆 | 增量 RSS | 耗时 |
|---|---:|---:|---:|
| loader 载入派生文件（基线 182 MB 堆 / 315 MB RSS） | — | — | 0.8 s |
| car 构图 + Graph | 459 MB | 436 MB | 3.8 s |
| walk 构图 + Graph | 570 MB | 609 MB | 4.5 s |
| bike 构图 + Graph | 404 MB | 410 MB | 3.8 s |
| bus 构图 + Graph | 459 MB | 481 MB | 4.0 s |
| **car 完整运行时**（拓扑 + 禁转索引 + 禁转表 + GeoJSON 字符串） | **1080 MB** | **1341 MB** | **6.3 s** |
| **walk 完整运行时** | **1235 MB** | **1373 MB** | **8.2 s** |
| 四模态构图全部持有 | 1892 MB | 1936 MB | 25.6 s |
| 四模态完整运行时全部持有 | **≈ 2.5 GB** | **≈ 3.0 GB** | — |

结论：**完整运行时**（含禁转索引）单模态已超 1 GB，禁转索引与禁转表各复制一份边集是主要增量，因此只有「同模态共用一份运行时」才在内存预算内。

### 运行期语义

- `GET /api/network?mode=X` 只用模态拓扑的准入结果生成要素，**不构建 Graph 与禁转索引**，首次约 1–2 s，之后命中 GeoJSON 缓存约 0.1 s。
- `GET/PUT /api/intersections/:nodeId/turns?mode=X` 需要该模态的禁转服务，首次请求触发完整运行时构建（武汉约 5 s），之后命中 LRU 缓存为毫秒级。
- `GET /api/transfer-points?mode=X` 直接来自派生文件的转换点标记，不依赖模态图，恒为毫秒级。
- LRU 淘汰的是运行时，**不影响已保存的禁转**：禁转写盘优先，落 `data/derived/wuhan-turns.sqlite`，重启后按「way 段端点 + 几何」重新匹配恢复。
- 边 ID 按构边顺序生成，**只在所属模态内有效**；`car` 与 `walk` 下同一路口的 `fromEdge`/`toEdge` 不通用，编辑器读写必须带同一个 `mode`。

### 已知代价

- 切换模态后第一次请求转向接口会明显变慢（约 5 s），因为该模态的运行时被 LRU 淘汰后需重建；演示前建议先访问目标模态。
- 若要保留两个模态常驻，可把 `createModalRuntimeRegistry` 的 `capacity` 调到 2，代价是堆占用增加约 1 GB。

### Node 运行基线（A 决策，issue #33）

`node:sqlite` 于 Node 22.5.0 引入，**22.13.0 起不再需要 `--experimental-sqlite` 标志**（上游文档「SQLite is no longer behind `--experimental-sqlite` but still experimental」）。因此 `engines.node` 收紧为 `>=22.13.0`，启动命令不加标志；22.x 下会打印 `ExperimentalWarning: SQLite is an experimental feature`，这是上游仍处实验阶段的事实，不做屏蔽。Node 24 LTS 起该模块稳定性提升到 release candidate。

## A 决策：跨模态路径契约与 bus 语义边界（2026-11-04，issue #34）

### 1. `PathResult` 是否扩展为多段结构 → 采纳「可选扩展」

**决策**：在 `PathResult` 上增加**可选**字段 `segments?: PathSegment[]`，不新造类型，也不让前端拆成多次调用。已冻结进 `shared/src/index.ts`：

```ts
export interface PathSegment {
  mode: TravelMode;              // 本段模态
  distance: number;              // 本段代价（米；时间口径下为秒）
  nodeIds: number[];             // 本段节点序列
  edgeIds: number[];             // 本段边序列，边 id 只在本段模态内有效
  coordinates: [number, number][]; // 本段折线 [lon, lat]
  fromTransferPoint?: number;    // 段起点转换点 id，首段缺省
  toTransferPoint?: number;      // 段终点转换点 id，末段缺省
}
```

理由：

- **非破坏性**：单模态路径缺省该字段，作业一/作业二现有客户端与测试不受影响；
- **一次调用返回整条跨模态路径**，前端可画一条连续路线并按段着色，不必在前端重新推导段序与换乘点；
- **与已冻结的 `TransferPoint.id` 直接衔接**：段间换乘用 id 表达，不需要新的转换点数据结构；
- **不依赖 C 的吸附实现细节**：吸附规则（每个模态吸附到哪个节点、接驳距离阈值）属数据侧诊断，不进契约，避免先冻结错形状。

约束：

- 段内边 id 只在所属模态内有效，跨段不可复用；
- `PathResult.distance` 为各段距离之和；**换乘惩罚（等待 + 接驳）属时间/成本口径，不计入距离**；
- 首段 `fromTransferPoint` 缺省、末段 `toTransferPoint` 缺省。

未采纳的替代方案是「前端多次调用后拼接」：换乘点、段序与总代价要在前端重新推导，容易出现与后端不一致的展示，且答辩讲「一段路怎么算出来的」时没有统一口径。

### 2. 公交模态的语义边界

**决策**：作业二**不做公交线路级建模**。bus 仅表示「公交通行道路」（`motorRoads + busway`），不含线路走向、站序、班次与停站规则。

因此：

- 「乘公交」的跨模态路径，本质是「沿 bus 可通行道路行驶/步行 + 换乘」，**不代表真实公交线路可达**；
- 答辩口径：bus 模态证明的是多模态分离与转换点的可行性，不是公交调度；
- 若教师后续要求线路级，需新增 relation 解析与站点匹配——`route`/`public_transport` relations 已在派生数据中保留（relations 共 353 条，含 102 条 restriction），但属于新的工作量，不在作业二范围内。

## 跨模态路径的实现口径（A 决策 + 实测，issue #34，2026-11-06）

契约早已冻结（`PathResult.segments`），本节记录**实现**时的口径与取舍，供答辩与后续标定使用。

### 1. 换乘连接从哪里来：转换点 → 模态节点对

转换点（`TransferPoint`）只是「这里有个地铁站/公交站/停车场」的标记，它**不是**路网上的节点，不能直接当换乘位置。实现分三步：

| 步骤 | 做法 | 依据 |
|---|---|---|
| ① 匹配 | 对每个模态，用 C 的 `matchTransferConnections` 找出该模态图上离设施最近的节点，并保留**证据类型** | `server/src/topology/transfer-connections.ts` |
| ② 连边 | 只有两个模态各自都有节点、且两者之间的**接驳距离**在上限内，才建立 `模态A 节点 ↔ 模态B 节点` 的连接 | `server/src/api/transfer-links.ts` |
| ③ 加权 | 换乘罚时 = 接驳步行时间（接驳距离 ÷ 1.3 m/s）+ 等待时间（`transferPenaltySeconds(kind)`，占位值） | C 的 `computeTransferPenalty` + D 的 `transferPenaltySeconds` |

**证据类型必须随连接一起保留**：

- `shared-osm-node`（452 条）：设施自身的 OSM 节点就是该模态图的节点——同一个节点，连接在节点层面是精确的；
- `nearby-candidate`（1995 条）：设施节点不在该模态图里，取半径内的最近节点——**只是几何近似，未做实景核验**。

way 型设施（停车场、站台面）一律**不建连接**：C 的匹配器直接判为 `entrance-required`，因为包围盒中心不是出入口。这样做的代价是换乘点数量偏少，收益是**不会把连接接到一条根本不存在的路上**。

### 2. 阈值与代价口径

| 参数 | 取值 | 说明 |
|---|---|---|
| 近邻候选半径 | car/bike/bus 100 m，walk 200 m | 设施节点到该模态路网节点的最远搜索距离 |
| 接驳距离上限 | car/bike/bus 100 m，walk 200 m | 两个模态节点之间的实际步行距离上限（issue #34 给的步行接驳阈值 200 m） |
| 接驳步行速度 | 1.3 m/s（约 4.7 km/h） | 用于把接驳距离换算成时间 |
| 等待时间（占位） | 地铁 5 分 / 公交 3 分 / 停车 5 分 | D 的 `transferPenaltySeconds`，**未标定**，标定计划见 `docs/plans/d-sprint2-weights-stats.md` §2 |

成本模型：`metric=time` 时总代价 = Σ段内时间 + Σ换乘罚时；`metric=distance` 时总代价 = Σ段内里程，**换乘罚时不计入**（按冻结契约，换乘惩罚属时间/成本口径）。为了让前端仍能显示等待时间，`PathResponse` 增加可选字段 `transferPenaltySeconds`，与 `distance` 分开下发。

### 3. 搜索：分层动态规划，不是「遇到第一个换乘点就换」

跨模态搜索在 B 的图引擎里实现（`server/src/graph/multimodal-dijkstra.ts`），状态空间是 **(模态, 节点, 入边)**：

- **层内**沿用 `(节点, 入边)` 边扩展状态空间，因此**禁转在跨模态路径里同样生效**；
- **层间**用动态规划推进：第 i 层先算出「到每个候选换乘点的最小代价」，再把每个可达换乘点作为第 i+1 层的源（初始代价 = 到达代价 + 换乘罚时），因此总代价是全局最优，而不是贪心取第一个换乘点；
- 层内搜索支持多源与「到达目标即可早停」，回溯时保证路径代价与记录的 dist 自洽。

### 4. 接口

```
GET /api/path?from=lon,lat&to=lon,lat&metric=time&modes=car,walk
```

- `modes` 是**逗号分隔的有序模态序列**（至少两个），语义：先按 `modes[0]` 行驶，在转换点换乘到 `modes[1]`，依次类推；
- 与单模态的 `mode` 参数**互斥**（混用返回 400）；
- 响应仍是冻结的 `PathResponse`，跨模态时 `segments` 有值：每段给模态、段内代价、节点/边序列与折线，段间以 `TransferPoint.id` 相接；
- 跨模态时顶层 `edgeIds` 为空——边 id 只在所属模态内有效，由 `segments[i].edgeIds` 承担；顶层 `nodeIds` 是各段节点序列的拼接（OSM 节点 id 跨模态通用）。

单次跨模态查询（首次，含两个模态运行时构建 + 连接表 + 两轮边扩展 Dijkstra）实测约 15 s，之后命中运行时缓存会明显更快；演示前建议先访问目标模态。

**答辩素材（真实场景）**：武汉「积玉桥 A 口」地铁站附近 134 m 有一个点型停车场（换乘连接证据为 `shared-osm-node`，接驳距离 0 m），可演示「驾车 → 停车场换乘 → 步行经过地铁站 → 步行到目的地」；另有「武胜路」地铁站 44 m、「江汉路」189 m 等组合。

### 6. 已知代价与边界

- **内存**：跨模态查询要同时持有两个模态的图与禁转索引（武汉实测 car + walk 约 2.3 GB 堆），比单模态查询明显更重；这是「同时用两套路网」的固有代价，设计取舍已在「装载策略」一节记录；
- **换乘罚时未标定**：等待时间是占位值，标定需要实景换乘数据与作业三的时间槽模拟；
- **地铁乘车未被建模**：`TravelMode` 没有 rail，地铁站只归属 walk，因此「驾车 → 地铁 → 步行」在本模型里表现为「驾车 → 换乘点 → 步行（途经地铁站）」，**不代表地铁线路级可达**，与「不做公交/地铁线路级建模」的决策一致；
- **近似连接**：1995 条连接是几何近似而非实景核验，答辩时应说明这一点，不要把它说成「已核验的出入口」。
