## 1. 项目概述

### 1.1 背景

课程要求以小组形式在 12 周内通过 4 次作业迭代，交付一个完整可运行的路网建模与拓扑构建系统。系统需支持有向图构建、转向限制、多模态路网、路网压缩与权重管理，并提供路网可视化编辑器和拓扑验证工具。核心算法（有向图、Dijkstra、A*、度-2 压缩、转向限制模型）必须自行实现，禁止调用第三方同名算法库（数据结构库允许）。

### 1.2 项目目标

构建一个 **B/S 架构的路网建模系统**：Node.js 服务端持有路网图模型与全部算法，浏览器客户端负责可视化与交互编辑。最终交付一个在评委电脑上一键启动、浏览器访问、支持 10 万+ 道路流畅渲染的完整程序。

### 1.3 硬性约束（来自任务书）

1. 核心算法自写，不可调用 OSRM / pgRouting / networkx 路径算法等第三方同名实现；`heapq`、优先队列等数据结构库明确允许。
2. 每次作业必须包含可视化（GUI/网页/图表/地图渲染），不接受纯命令行输出。
3. 每次作业提交可编译运行的源代码；最终交付一键运行，评委电脑直接跑。
4. 全程记录 AI 使用日志；答辩随机抽取核心函数解释，解释不清视为抄袭。
5. 第 4 次作业需 10 万+ 道路渲染不卡顿，A* 路径搜索过程可视化演示。

### 1.4 数据来源

G1 组的标准化数据（自定义格式 / GeoJSON / SQLite），或教师提供的备份数据。第 4 次作业增加 OSM XML 导入能力（自行解析，作为导入功能而非解析器交付）。

### 3.3 核心模型设计详述

#### 3.3.1 计算分层：内存图与数据库的分工

路径算法在服务端内存图上运行，而不是在数据库中执行，依据有三。

其一，**访问模式不匹配**。Dijkstra 是迭代式随机访问算法：弹一次堆、看一圈邻居、改几个距离值，10 万节点的图要做数十万到上百万次这样的微操作。内存中一次邻接表查找加一次堆操作在纳秒到微秒级且命中 CPU 缓存；数据库中每条 SQL 即使简单到极致也有解析、计划、索引查找、行物化的固定开销，逐条执行数十万次即从毫秒级劣化到秒级以上。用 WITH RECURSIVE 把整个算法写成一条递归查询虽然能出结果，但更慢、不可维护，答辩也无法解释。

其二，**数据结构不匹配**。算法依赖带 decrease-key 的优先队列、O(1) 迭代出边的邻接表、按下标随机访问的 visited/parent 数组，关系模型均无法自然表达。叠加课程硬性约束——核心算法自写、禁止第三方同名算法库（pgRouting 等图算法扩展直接出局）——堆优化的 TypeScript 实现接近伪代码，是答辩讲解成本最低的形态。

其三，**数据库的强项另有所在：集合操作**。里程统计、等级分布、可达性汇总本质是 GROUP BY，直接在 SQLite 上跑 SQL 简洁高效。由此确立分层原则：**数据库管持久化与集合查询，服务端管迭代计算**。

工业界佐证：OSRM、Valhalla 及主流商业导航引擎均为启动时将路网载入内存紧凑结构；pgRouting 的"库内算法"同样运行在数据库进程的内存中。真正的分界不是"库上还是内存"，而是"通用查询引擎的逐行开销"与"为算法定制的数据结构"之分。本项目的性能预算（A* < 100ms @ 10 万节点）只有内存图能达标。

#### 3.3.2 转向限制：状态空间与存储设计

**问题定义**：转向限制约束的不是节点，而是 (入边, 出边) 对——"从人民路进入路口 C 后禁止左转向北"。节点图的搜索状态只有"我在 C"，丢失了来路信息，支配性剪枝因此出错：设到达 C 有两条路径，经西边代价 5、经南边代价 8，目的地在北边；节点图保留代价 5、剪掉 8，但"经西边左转去北"被禁，真正可行的是被剪掉的"经南边直行去北"。错误不在算法，在状态定义缺失"入边"维度。

**模型**：边扩展状态空间——搜索状态 = (节点, 入边)，转移 = 从入边末端驶向某条出边且该转向未被禁止；起点映射为起点的全部出边，终点判定为到达任一"末端为目标节点"的边，路径还原产出边序列（自带几何与节点顺序）。

**存储方案（稀疏表 + 懒查，不物化 EEG）**：

```ts
// 默认所有转向允许,只记录被禁的:
// nodeId → fromEdgeId → Set<forbidden toEdgeId>
const forbidden: Map<number, Map<number, Set<number>>>;

// 搜索状态携带入边,松弛出边时查一次表
状态 = (node, inEdge);
for (const f of graph.outEdges(node))
  if (!forbidden.get(node)?.get(inEdge)?.has(f.id)) relax(f);
```

不预建 O(E) 规模的展开图：编辑器修改限制即改表项、立即生效（作业 2 要求"点击路口实时设置/取消转向"），内存占用更小，是物化 EEG 的等价替代。

**被否决的备选方案**：节点级"允许左转/右转/直行"标签。评审结论：

1. "左转"不是节点属性而是 (来向, 去向) 属性——同一"禁左"作用于西向入边封掉"去北"，作用于南向入边封掉"去西"，节点自身没有"左边"；
2. 剪枝正确性要求搜索状态携带入边，与限制存储在节点还是边对上无关，存储简化救不了状态定义缺陷；
3. 表达力不足——现实中常只禁单方向左转（北侧进口禁左、南侧照常），"专用车道"按进口道定义，节点级标签只能过度限制；
4. OSM 的 turn restriction 原生为 (from way, via node, to way) 三元组，作业 4 导入 OSM 必须按边对存储。

**多路口（>4 条边）节点**：五路口、立交匝道汇入点、双幅路交叉口在真实路网中大量存在。N 个进方向节点的转向动作数为 N×(N−1)，6 路口即 30 个动作，四分类标签既不够用也有歧义（可能两条出边都偏左、两条都偏右）。边对枚举对任意 N 成立，核心模型无需修改；调整仅在显示层——方位角差落入明确区间显示四分类标签，模糊地带回退显示目标道路名 + 偏角（如"驶入建设南路（左偏 75°）"），与成熟导航产品的复杂路口策略一致。

**设计原则**：给人看标签，给机器存对。几何标注用于 UI 展示，存储与算法判定一律使用 (fromEdge, toEdge) 边对。

**验证要求**：Sprint 2 spike 必须包含目标城市一个真实五路口的转向限制用例，一个用例同时覆盖状态空间、稀疏表与编辑器显示三层，并作为答辩演示素材。

## 4. 敏捷生命周期规划

### 4.2 协作边界机制（目标：任何人都不需要修改他人的代码）

分工表中的"唯一修改权目录"通过以下机制强制执行，而不是停留在口头约定：

1. **契约先行**：Sprint 0 由 A 在 `shared/` 冻结全部跨模块契约——领域模型（Node/Edge/PathResult）、路径计算入参与出参、SearchTrace 回放数据格式、WS 消息结构、权重注入接口。此后所有跨模块调用只经由 `shared/` 类型与各模块 `index.ts` 公开入口进行。
2. **目录所有权 + CODEOWNERS**：仓库根目录放置 `CODEOWNERS` 文件，将分工表中每个目录映射到唯一 owner；平台强制"非 owner 触碰该目录的 PR 必须由 owner 审批"，默认拒绝合并。
3. **变更流程**：任何成员发现上游接口不满足需求时，提"契约变更" issue → A 召集受影响 owner 评估影响面 → 先修改 `shared/` 契约 → **各 owner 自行修改自己的模块适配新契约**。需求方全程只提 issue、不动他人代码——"谁的代码谁自己改"。
4. **并行开发不互相阻塞**：契约冻结当天，A 提供样例数据与 mock 接口；前端（D/E）按契约对接 mock 开发，后端（B/C/D）按契约先写 Vitest 单测，联调只发生在边界上。
5. **lint 强制边界**：ESLint `no-restricted-imports` 禁止跨目录引用非 `index.ts` 入口，越界引用 CI 直接报错，不靠自觉。
6. **集成节奏**：main 分支保护 + PR 小步合入；A 每日集成一次并跑全量测试，PR 描述必须注明"是否涉及契约变更"。

这套机制的额外收益：答辩讲架构时，"模块边界 = 目录边界 = 所有权边界"三位一体，职责划分一页讲清。

### 4.3 Sprint 计划

#### Sprint 0 · 第 1 周 · 立项与地基

**目标**：走通"数据 → 服务端 → 浏览器渲染"一条最短链路。

- [ ] 仓库初始化（monorepo：`server/` + `web/` + `scripts/`），分支保护与 PR 流程
- [ ] Vite + TS + MapLibre 在线底图 + deck.gl 空图层跑通（深色底 + 路网占位数据）
- [ ] Fastify 服务 + `/api/health` + WebSocket 通道打通
- [ ] 用教师备份数据（或 G1 现有样例）解析出 nodes/edges 并入库内存
- [ ] 立项文档、AI 日志模板、GitHub Projects 看板建立

**验收**：`npm run dev` 一条命令，浏览器看到底图 + 占位路网点选弹出属性。

#### Sprint 1 · 第 2–3 周 · 作业 1：路网拓扑构建基础 → **M1（第 4 周提交）**

**目标**：真实的节点-边有向图 + 拓扑验证 + 基础可视化。

- [ ] `Graph` 有向图类（邻接表，Float32Array 紧凑坐标）；单行道/双向道/motorway 默认单向规则
- [ ] 连通分量（并查集）、度分布统计、悬挂节点检测
- [ ] Dijkstra（`PriorityQueue` 自实现或标准库堆）+ 路径重建
- [ ] 前端：GeoJSON 路网渲染、按 highway 等级着色、缩放/平移、点选道路属性面板
- [ ] 起终点点击 + 路径高亮显示（距离/时间）
- [ ] 拓扑验证报告（连通分量数/悬挂节点数/平均度）+ 设计文档 + AI 日志

**验收（对照考核）**：有向图正确支持单行道（30%）｜拓扑构建正确（20%）｜图算法正确（15%）｜可视化交互流畅（20%）｜文档报告（15%）。

#### Sprint 2 · 第 5–6 周 · 作业 2：转向限制与多模态 → **M2（第 7 周提交）**

**目标**：边扩展图模型落地，转向限制真正影响路径结果。

- [ ] 转向限制状态空间：(node, inEdge) 懒查稀疏禁转表（设计见 3.3.2）；Dijkstra/A* 兼容有无限制两种模式
- [ ] 转向限制数据模型（禁左转/禁掉头/专用车道）+ SQLite 持久化；spike 含真实五路口用例
- [ ] 转向限制编辑器：点击路口 → 面板列出全部转向（几何标注左/右/直/掉头，复杂路口回退显示目标路名+偏角）→ 禁止转向渲染为红色弧线
- [ ] 四模态子图（同一 Graph 类按 mode 过滤）+ 模态转换点（地铁/公交站/停车场）标记
- [ ] 前端模态一键切换图层；跨模态路径验证（驾车→地铁站→步行）
- [ ] 多模态设计文档 + 编辑器演示 + AI 日志

**验收**：转向限制正确影响路径（25%）｜多模态设计与转换正确（25%）｜编辑器直观（20%）｜与 M1 集成（15%）｜文档演示（10%）。

#### Sprint 3 · 第 8–9 周 · 作业 3：路网压缩与权重管理 → **M3（第 10 周提交）**

**目标**：压缩与权重形成可量化的对比报告。

- [ ] 度-2 节点压缩（直行链合并）+ 压缩图/原图双向映射（路径还原）
- [ ] 动态权重模型：等级系数 × 限速 × 拥堵系数（时间槽函数模拟）
- [ ] 权重配置面板：滑杆调整系数，实时触发重算与重着色
- [ ] 可视化：按拥堵程度/车速着色、权重时间变化动画（requestAnimationFrame 时间轴）
- [ ] 统计分析：里程统计、等级分布、连通性、可达性（等时圈）+ ECharts 图表
- [ ] 压缩前后对比报告（节点数/边数/查询耗时）；CH 可选加分（时间富余才做）
- [ ] 文档 + AI 日志

**验收**：压缩正确且效果明显（25%）｜动态权重合理影响路径（25%）｜权重可视化直观（20%）｜统计完整（15%）｜文档报告（15%）。

#### Sprint 4 · 第 11–12 周 · 作业 4：完整路网建模系统 → **M4（第 12 周提交）**

**目标**：从"模块拼贴"到"完整产品"，答辩就绪。

- [ ] 路网编辑器：添加/删除/移动节点与道路，操作经服务端更新拓扑并广播刷新
- [ ] 导入导出补全：OSM XML 导入（自解析 highway/oneway）、GeoJSON/自定义格式双向
- [ ] A* 搜索过程回放动画：访问节点扩散 + 边界集合 + 最终路径三态渲染，支持暂停/倍速/进度条
- [ ] 性能冲刺：10 万+ 边视口裁剪压测、LOD（用度-2 链）、加载 < 5s、渲染 60fps
- [ ] 集成联调 + 全流程回归（M1–M3 功能不退化）
- [ ] 交付物：用户手册、设计文档、API 文档、3–5 分钟演示视频、答辩 PPT、AI 完整日志、start 脚本在干净环境验证

**验收**：功能完整（25%）｜编辑器流畅（15%）｜大规模渲染性能（15%）｜A* 演示直观（15%）｜代码文档（15%）｜答辩（15%）。

#### 收尾 · 第 12 周后 · 答辩准备

演示彩排（模拟评委抽问核心函数）、备用视频与离线环境最终确认、回顾会沉淀。

### 4.4 Definition of Done（每次作业的完成定义）

1. 功能全部实现且在干净机器上一键运行通过（无 Node 环境的机器验证便携方案）；
2. 可视化演示流畅，现场可交互；
3. 源码合入 main——改动仅限本人所有目录，确需触碰他人目录必须获该 owner 评审通过；Vitest 算法测试全绿；
4. 设计文档/使用说明/API 文档更新至当次范围；
5. AI 使用日志如实更新；
6. 核心函数组内轮讲通过——每人能讲清任一核心函数的输入输出与原理（防答辩抽问）。

## 8. 质量与度量

- **对齐考核的自查表**：每次提交前按六维度（功能/代码/可视化/文档/AI 日志/答辩）逐项打分自查，低于 80% 的项当周补救。
- **性能预算**（作业 4 硬指标）：10 万+ 道路渲染稳定 60fps；路网加载 < 5s；A* 查询（10 万节点级）< 100ms；启动 < 3s。
- **代码质量**：ESLint + Prettier；核心模块（`server/src/graph`）注释覆盖 100%，函数级 JSDoc（答辩讲解素材）；关键算法 Vitest 单测（Dijkstra 最优性、压缩往返一致性、禁转用例集）。
- **敏捷度量**：Sprint 燃尽图（GitHub Projects 自动生成）、每期回顾会改进项落实数、风险登记册更新频率。

## 9. AI 使用日志规范（课程硬性要求）

每次使用 AI 工具记录一行，周五由 Scrum Master 归档：

| 字段 | 说明 |
|---|---|
| 日期 / 工具 | 如 2026-XX-XX · Claude |
| 用途与 Prompt 摘要 | 例如"生成分裂堆 Dijkstra 实现" |
| 采纳程度 | 直接采纳 / 修改后采纳 / 仅参考 / 弃用 |
| 修改说明 | 改了什么、为什么（变量命名/边界条件/数据结构替换） |
| 理解自评 | 能否向他人解释该段代码（1–5），<4 的必须组内讲解 |
| 关联提交 | commit / PR 链接 |

> 原则：AI 生成的核心算法代码必须**逐行理解并重命名重构**后才可合入 main——这是对答辩抽问最直接的保险。
